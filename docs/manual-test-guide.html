TIMEZONE S2 — Brazil IP / São Paulo Timezone 5 cases
1locale=BR trả valid response
Setup — tính ngày mai theo giờ São Paulo (UTC−3)
# Nếu giờ UTC hiện tại < 03:00 → ngày mai SP = HÔM NAY UTC # Nếu giờ UTC hiện tại ≥ 03:00 → ngày mai SP = NGÀY MAI UTC # Ví dụ: UTC 2026-06-22 01:00 → SP đang là 2026-06-21 22:00 → ngày mai SP = 2026-06-22
Request
POST /scheduled-events-pagination-v2/{SP_TOMORROW}/locale/BR/type/upcoming Body: {"sortByMatchTime": false}
PASS khi code=1, events là array, otherCompetitions là array
2[BUG CORE] DB count = API total — ngày mai SP
Cửa sổ thời gian đúng cho São Paulo
# Ngày D ở SP = UTC từ D 03:00:00 đến D+1 02:59:59 # Ví dụ: ngày mai SP = 2026-06-22 # → UTC window: 2026-06-22T03:00:00Z đến 2026-06-23T02:59:59Z
Query DB
SELECT COUNT(*) FROM sport_events WHERE start_timestamp >= UNIX(2026-06-22T03:00:00Z) AND start_timestamp < UNIX(2026-06-23T03:00:00Z) AND status_id IN (0, 1) -- not_started
So sánh
  • DB.not_started ≈ API.total (±5)
  • Nếu DB > API + 5 → server đang bỏ sót trận → bug timezone
PASS khi |DB.not_started - API.total| ≤ 5
⚠ Đây là test cốt lõi phát hiện timezone bug. Hiện tại: DB=87, API=87 ✓
3[BOUNDARY] Trận 21:00–23:59 SP phải có trong response
Vùng nguy hiểm
# 21:00–23:59 SP ngày D = 00:00–02:59 UTC ngày D+1 # Đây là phần bị mất nếu server dùng UTC day boundary thay vì SP boundary
Query DB — đếm trận trong boundary
SELECT COUNT(*) FROM sport_events WHERE start_timestamp >= UNIX(D+1 00:00 UTC) AND start_timestamp < UNIX(D+1 03:00 UTC) AND status_id IN (0, 1)
Verify
  • Nếu DB có trận trong boundary (> 0)
  • Thì API.total phải ≥ boundary_count
PASS khi API không bỏ sót trận trong khung 21:00–23:59 SP
